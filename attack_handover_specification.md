## 2. Attack Mechanics & Defender Indicators

### Flagship 1: Prompt Injection via Merchant Content
*   **The Vector:** Indirect Prompt Injection.
*   **How it works:** The user asks the assistant to buy an item. The assistant queries merchant information via `get_payee_details()`. The page text (loaded from [merchant_pages.json](file:///c:/Users/Sweety%20gupta/Desktop/pw_4/generate/fixtures/merchant_pages.json)) contains hidden instruction overrides. The assistant follows these instructions and redirects the payment to an attacker wallet (e.g. `REF-99213-ATTACKER` or `FRAUD-77410-STEAL`).
*   **Defender Strategy (Deterministic Gate):**
    *   The simulated payment assistant flags this call by passing `source_of_instruction: "external_content"` to the `transfer_funds()` tool.
    *   **Rule:** Intercept any payment where `source_of_instruction == "external_content"`. Trigger step-up verification or freeze transaction immediately.

---

### Flagship 2: Multi-Turn Context & Trust Poisoning
*   **The Vector:** Social Engineering / Conversational Poisoning.
*   **How it works:** An external actor (scammer) initiates a multi-turn chat using a persona (Romance, Fake Support, Friend of a Friend) from [personas.json](file:///c:/Users/Sweety%20gupta/Desktop/pw_4/generate/fixtures/personas.json). Over 6-8 turns, they build rapport, casually mention a payee account ID, and then fabricate an emergency (like hotel money or account lockout) requesting a transfer.
*   **Defender Strategy (ML Classifier):**
    *   **Rule Gate limitation:** The payment call will declare `source_of_instruction: "user_explicit"` because the user (acting under deception) explicitly ordered the assistant to make the transfer. Simple rules will not catch this.
    *   **Feature Engineering:** Extract conversational features from the transcript history:
        *   Turn count (usually 5+ turns of dialogue prior to payment).
        *   Rapport/sentiment words (e.g., *dear, compliance, verification, urgent, safe vault*).
        *   Check if payee ID was introduced by the user during the chat rather than checking standard databases.
        *   Presence of romance scam indicators or fake compliance support requests.

---

### Flagship 3: Recommendation Bias & Memory Poisoning
*   **The Vector:** System Instruction Override / Decision Hijacking.
*   **How it works:** The user asks for financial or shopping advice (*"where should I invest my savings?"*). The assistant consults review blogs (from [biased_investments.json](file:///c:/Users/Sweety%20gupta/Desktop/pw_4/generate/fixtures/biased_investments.json)) containing injected commands (e.g. promoting `APEX-GROWTH-NODE` using falsified AAA metrics). The assistant is manipulated into pitching the biased asset and starting a transfer.
*   **Defender Strategy (ML Classifier & Auditing):**
    *   **The Indicator:** Taint check the recommended payee ID against the retrieved document context. 
    *   **Behavioral Feature:** Check for semantic anomalies. If the agent recommends a single asset while suppressing competing options retrieved during lookup, flag as **Steering/Recommendation Bias**.

## 3. Legitimate Baseline (The Control Group)

*   **Role:** Transcripts generated by [generator_legitimate.py](file:///c:/Users/Sweety%20gupta/Desktop/pw_4/generate/generator_legitimate.py) containing safe everyday transfers (monthly rent, split bills).
*   **Why it matters:** They exhibit high surface similarity (e.g. user requests an urgent rent payment to a new landlord account).
*   **Defender Strategy:** Use this dataset as the negative class (`ground_truth_label: "legitimate"`) to train your ML models. This prevents the classifier from incorrectly flagging all urgent transactions as fraud.
